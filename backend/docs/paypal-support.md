# Private PayPal support foundation

Verified against official [Orders v2](https://developer.paypal.com/api/orders/v2), [Subscriptions v1](https://developer.paypal.com/api/subscriptions/v1), and [webhook verification](https://developer.paypal.com/api/rest/webhooks/rest/) references on 2026-10-08. This integration is for optional support from invited friends and family. It never grants access or changes quotas.

Every environment starts disabled. The administrator needs a suitable PayPal merchant/Business account, a REST app with Checkout and Subscriptions capabilities, a registered webhook ID, and DKK receiving settings. Store the sandbox and live client ID, client secret, receiving merchant ID and webhook ID separately through the admin API. The client secret is encrypted. Enabling live checkout requires recent reauthentication and explicit `confirmLive: true`. No account, product, plan, charge, refund or cancellation is created on startup. Only the two official PayPal API origins are used. The browser receives only PayPal-hosted approval URLs; Homelabrrr does not collect card data.

A monthly plan must be set up deliberately in PayPal. The configured plan is validated on enable: one regular monthly cycle, DKK fixed price matching the configured amount, no trial or setup fee, and `auto_bill_outstanding: false`. Changing an amount requires a new plan and renewed payer approval. Disabling new checkout **does not cancel existing subscriptions**. Members can request cancellation via their own subscription ID; the provider state must be checked before reporting it confirmed.

The webhook endpoint `/api/payments/paypal/webhook/:environment` is the sole unauthenticated ingress. The reverse proxy must make only this HTTPS path reachable to PayPal. It receives raw JSON before the app's cookie and CSRF middleware, sends the original event bytes to PayPal's verify-webhook-signature endpoint with the configured webhook ID, then durably stores the event before acknowledgment. Invalid signatures fail closed. A background inbox worker resumes persisted events after restart. PayPal's simulator events do not support postback verification and are not treated as verified payment tests.

Amounts are integer øre. Gross is positive; a provider-reported fee is negative. The reported net amount is a consistency check, not another posting. Missing fee or net means `net_unresolved`, not fee zero. Sandbox postings must never be included in live budget totals. The economic reference is unique per environment, merchant, transaction and posting kind. Browser redirects and subscription activation are never receipts. Month allocation and complete provider adjustment coverage remain outstanding; do not treat this as production-ready accounting or enable live checkout until those paths and integration tests are complete.

## Reconciliation and posting contract

A six-hour bounded pass checks at most ten uncertain one-off orders and ten mapped subscriptions per environment. Subscription transaction queries cover at most 30 days and overlap the previous cursor by seven days. A failed or truncated response does not advance the cursor. Administrator resync is limited to one request per environment every five minutes. GET requests retry 429/503 at most twice, respecting `Retry-After` up to one minute; mutating payment calls are never blindly retried.

Completed subscription transactions use `amount_with_breakdown.gross_amount`, `fee_amount` and `net_amount`. A completed capture uses `seller_receivable_breakdown`. A completed v2 capture refund uses its own `seller_payable_breakdown`; the cumulative `total_refunded_amount` is not a new adjustment. Exact money postings use one economic ID per environment and merchant, with linked refund and fee-credit postings. Previously posted source values that change are flagged for review rather than silently overwritten. Missing fee/net is retained as unresolved and blocks finalized eligible net. Webhook sale completions are resolved through their mapped subscription transaction list, never sent to the v2 capture endpoint.

The six-hour pass reads a bounded, overlapping range from PayPal's authenticated app-scoped webhook event list and persists missed events into the same inbox. Normal intent, merchant and economic-ID checks still apply. A page with a `next` link fails reconciliation visibly rather than advancing past unseen events. Its 30-day lookup horizon cannot recover an outage older than that; operators must review coverage after a prolonged outage.

Sale refund/reversal and capture reversal notifications now request one exact transaction ID from PayPal Transaction Search (the merchant REST app needs its reporting read scope). Only a successful negative DKK adjustment with a `TXN` reference to a locally recorded sale/capture and an allowed refund/reversal transaction code may enter the append-only ledger. Actual positive fee credit comes from the reported transaction; missing fee stays `net_unresolved`. PayPal notes that reporting transactions can lag by up to three hours, so the inbox retries with bounded backoff and eventually marks unresolved events for review. Unexpected codes, currencies, references and amount signs remain held for review. Full allocation/credit ledgers and sandbox verification are still required before live activation. No real sandbox account or payment has been exercised.

Member deletion now requests cancellation of every linked nonterminal subscription and blocks the deletion until PayPal readback confirms `CANCELLED` or `EXPIRED`. The request ID is persisted for retries; a lost cancellation response is read back before another request. The six-hour worker prioritizes unresolved cancellation requests. Disabling checkout does not cancel recurring billing. A provider outage or missing credentials therefore leaves the account in place and requires operator follow-up rather than detaching its financial mapping.
