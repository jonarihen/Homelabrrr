# Private PayPal support foundation

Verified against official [Orders v2](https://developer.paypal.com/api/orders/v2), [Subscriptions v1](https://developer.paypal.com/api/subscriptions/v1), and [webhook verification](https://developer.paypal.com/api/rest/webhooks/rest/) references on 2026-10-08. This integration is for optional support from invited friends and family. It never grants access or changes quotas.

Every environment starts disabled. The administrator needs a suitable PayPal merchant/Business account, a REST app with Checkout and Subscriptions capabilities, a registered webhook ID, and DKK receiving settings. Store the sandbox and live client ID, client secret, receiving merchant ID and webhook ID separately through `/admin/paypal`. The client secret is encrypted. Enabling live checkout requires recent reauthentication and explicit `confirmLive: true`. No account, product, plan, charge, refund or cancellation is created on startup. Only the two official PayPal API origins are used. The browser receives only PayPal-hosted approval URLs; Homelabrrr does not collect card data. Set `PORTAL_BASE_URL` (or `ALLOWED_ORIGIN`) to the exact HTTPS portal origin so PayPal can return to `/support`. The redirect alone never confirms a receipt.

A monthly plan must be set up deliberately in PayPal. The configured plan is validated on enable: one regular monthly cycle, DKK fixed price matching the configured amount, no trial or setup fee, and `auto_bill_outstanding: false`. Changing an amount requires a new plan and renewed payer approval. Disabling new checkout **does not cancel existing subscriptions**. Members can request cancellation via their own subscription ID; the provider state must be checked before reporting it confirmed.

The webhook endpoint `/api/payments/paypal/webhook/:environment` is the sole unauthenticated ingress. The reverse proxy must make only this HTTPS path reachable to PayPal. It receives raw JSON before the app's cookie and CSRF middleware, sends the original event bytes to PayPal's verify-webhook-signature endpoint with the configured webhook ID, then durably stores the event before acknowledgment. Invalid signatures fail closed. A background inbox worker resumes persisted events after restart. PayPal's simulator events do not support postback verification and are not treated as verified payment tests.

The inbox retains full provider event payloads for 30 days after successful processing so operators can investigate recent deliveries. A bounded worker then replaces each processed payload with an empty object. The event ID, environment, merchant, type, timestamps, processing result and economic ledger records remain for replay protection and accounting. Pending and review-required events keep their payload until resolved; operators should resolve these promptly because they may contain payer data.

Amounts are integer øre. Gross is positive; a provider-reported fee is negative. The reported net amount is a consistency check, not another posting. Missing fee or net means `net_unresolved`, not fee zero. Sandbox postings must never be included in live budget totals. The economic reference is unique per environment, merchant, transaction and posting kind. Browser redirects and subscription activation are never receipts. No real sandbox account or payment has been exercised; complete provider coverage and sandbox verification are required before live activation.

## Reconciliation and posting contract

A six-hour bounded pass checks at most ten uncertain one-off orders and ten mapped subscriptions per environment. Subscription transaction queries cover at most 30 days and overlap the previous cursor by seven days. A failed or truncated response does not advance the cursor. Administrator resync is limited to one request per environment every five minutes. GET requests retry 429/503 at most twice, respecting `Retry-After` up to one minute; mutating payment calls are never blindly retried.

Completed subscription transactions use `amount_with_breakdown.gross_amount`, `fee_amount` and `net_amount`. A completed capture uses `seller_receivable_breakdown`. A completed v2 capture refund uses its own `seller_payable_breakdown`; the cumulative `total_refunded_amount` is not a new adjustment. Exact money postings use one economic ID per environment and merchant, with linked refund and fee-credit postings. Previously posted source values that change are flagged for review rather than silently overwritten. Missing fee/net is retained as unresolved and blocks finalized eligible net. Webhook sale completions are resolved through their mapped subscription transaction list, never sent to the v2 capture endpoint.

The six-hour pass reads a bounded, overlapping range from PayPal's authenticated app-scoped webhook event list and persists missed events into the same inbox. Normal intent, merchant and economic-ID checks still apply. A page with a `next` link fails reconciliation visibly rather than advancing past unseen events. Its 30-day lookup horizon cannot recover an outage older than that; operators must review coverage after a prolonged outage.

Sale refund/reversal and capture reversal notifications now request one exact transaction ID from PayPal Transaction Search (the merchant REST app needs its reporting read scope). Only a successful negative DKK adjustment with a `TXN` reference to a locally recorded sale/capture and an allowed refund/reversal transaction code may enter the append-only ledger. Actual positive fee credit comes from the reported transaction; missing fee stays `net_unresolved`. PayPal notes that reporting transactions can lag by up to three hours, so the inbox retries with bounded backoff and eventually marks unresolved events for review. Unexpected codes, currencies, references and amount signs remain held for review. No real sandbox account or payment has been exercised.

## Monthly owner-cost allocation

An administrator can calculate an append-only monthly allocation through `/admin/paypal`. The calculation uses only confirmed **live DKK** postings and a single finalized electricity cost statement for each Copenhagen calendar month. Gross, actual fees, refunds, reversals and fee credits flow into net support. Missing fee/net, a review event, incomplete electricity cost, or multiple finalized contracts produces an explicit unresolved or unknown result. No unknown amount is silently assumed to be zero.

Each monthly row has a SHA-256 source fingerprint, revision, previous-row link, ledger revision, source cost statement and opening/closing balance. Repeating an unchanged calculation adds no row; a late receipt, refund or cost revision appends a new row and propagates to later months. A positive closing balance is credit carried forward. A negative balance after a late refund is an **owner-funded adjustment**, never a debt charged to a contributor. Calculation is bounded to 120 months and 100,000 postings; a source limit error requires operator review. Allocation currently runs by administrator request; it is not a claim that all historical provider adjustments have been reconciled.

Member deletion now requests cancellation of every linked nonterminal subscription and blocks the deletion until PayPal readback confirms `CANCELLED` or `EXPIRED`. The request ID is persisted for retries; a lost cancellation response is read back before another request. The six-hour worker prioritizes unresolved cancellation requests. Disabling checkout does not cancel recurring billing. A provider outage or missing credentials therefore leaves the account in place and requires operator follow-up rather than detaching its financial mapping.

## Verification boundary

`src/routes/payments.integration.test.ts` runs against a throwaway PostgreSQL database with all migrations applied and a fixed-origin PayPal HTTP fixture. It covers member/admin authorization, disabled checkout, hosted approval without a receipt, approved order capture, verified and rejected webhook delivery, duplicate-event replay, actual capture and subscription fees, refund postings, an unresolved fee, and subscription cancellation readback. No request reaches PayPal. A real PayPal sandbox account still needs checkout, subscription, webhook, settlement fee, refund and reconciliation verification before live checkout is enabled.

## Operator runbook (hardening update, 2026-10-11)

PayPal behaviour referenced here was rechecked against the official Orders v2, Payments v2, Subscriptions v1, Webhooks and Transaction Search references on 2026-10-11. No real sandbox or live account was used; every automated test runs against an injected HTTP fixture.

### Account and setup
1. Use a verified PayPal **Business** account whose receiving preferences accept DKK. A private account may not be eligible. Create a REST app per environment with Checkout and Subscriptions, plus the Transaction Search reporting scope needed for sale refund/reversal lookups.
2. In `/admin/paypal`, save the client ID, secret and receiving merchant ID. The secret is write-only. Leave it blank to keep the stored secret, which works only while the client ID is unchanged. Every save, enable and disable creates a new config version with a history row that holds no secret. A save from an outdated form (stale `expectedVersion`) is refused with `CONFIG_VERSION_CONFLICT`.
3. **Register webhook** creates the registration for `https://<portal>/api/payments/paypal/webhook/<environment>` with the required events, or reuses an existing registration for that URL. **Create product** and **Create monthly plan** are idempotent per environment and REST app. The `PayPal-Request-Id` is stored before each call, so retrying after a lost response returns the same resource instead of a duplicate. Created IDs must still be saved or offered explicitly.
4. **Test connection** is read-only. It gets a token, reads the webhook back (URL and events), and validates the configured plan. It never charges anyone.
5. Enable sandbox first. Live enablement needs recent reauthentication and explicit live confirmation.

### Reverse proxy
Only `POST /api/payments/paypal/webhook/<environment>` must be reachable by PayPal, over HTTPS. Keep the rest of the portal, iLO and Proxmox private (for example, allow-list that one path at the edge). Forward `X-Forwarded-Proto` so the backend can refuse plain HTTP. The route keeps raw bytes for signature verification and bypasses only session/CSRF. Per-client requests are limited (`PAYPAL_WEBHOOK_RATE_LIMIT_PER_MINUTE`, default 120). A 429 or 5xx makes PayPal redeliver, and an event is acknowledged only after it is verified with `SUCCESS` and durably stored.

### Monthly plans and failure behaviour
Plans created here use one regular monthly DKK cycle, no setup fee or trial, `auto_bill_outstanding: false` (a missed payment is never collected later) and `payment_failure_threshold: 1`, so PayPal suspends the subscription after one failed payment instead of retrying into debt. Admins can offer several validated plans, one per amount. Members choose only among offered amounts, and the plan ID is resolved and re-validated server-side. A member with a live subscription cannot start a second one. Changing the amount cancels the current subscription and waits for PayPal to confirm, and only then offers a new approval. Retiring a plan stops new approvals but does not cancel existing billing. Disabling checkout does not cancel subscriptions either.

### Reconciliation
The interval is `PAYPAL_RECONCILE_INTERVAL_MINUTES` (default 360, range 15–1440). A startup pass runs about two minutes after boot. Each pass:
- recovers missed webhook events. Validated `next` pages are followed (at most 20 per window), and the event cursor advances as soon as that step succeeds;
- reads back uncertain one-off captures, including `capturing` intents orphaned by a crash (after 10 minutes). Only an order PayPal still reports as `APPROVED` with no capture is captured again, with the persisted request ID, at most 5 times;
- reconciles subscriptions. Each one is isolated with its own exponential backoff, so one broken mapping cannot abort the pass. Transaction listing follows pages and splits windows when needed;
- retries missing fee/net detail and refund coverage for `net_unresolved` rows. Nothing is estimated.

A partial run is shown as `partial` with a failed-item count. Logs and metrics (`paypal_reconcile_failures`, `paypal_webhook_events`) carry only fixed labels: no IDs, amounts or payer data.

### Refunds, holds and currencies
A capture reported as `PARTIALLY_REFUNDED`, `REFUNDED` or `REVERSED`, or a sale reported as partially/fully refunded, keeps an adjustment placeholder unresolved. That blocks finalized net until every refund is recorded. Capture refunds are listed from the order readback. Sale refunds arrive by verified event, and a partial sale refund also waits until missed-event recovery has passed the time the refund was first seen. Pending captures/sales, denials and disputes are tracked separately: they are shown but never subtracted, because only an actual refund or reversal posting reduces net. Non-DKK settlement amounts are stored verbatim and never summed into DKK.

### Review queue and manual transfers
`needs_review` events block finalized net. **Retry** sends an event back through verified processing. **Dismiss** requires reauthentication and a note, records the event as not lab income and posts nothing. Members can report a bank transfer, but the report never posts. An admin confirms it with evidence, which posts one live DKK receipt (merchant scope `manual`). References matching an imported PayPal transaction are refused, a nearby same-amount PayPal receipt from the same member requires an explicit override, and a correction appends a reversal. Ledger CSV export requires reauthentication, is audited, and escapes formula-like cells.

### Simulator limits
PayPal's webhook simulator sends events that cannot pass `verify-webhook-signature`, so they are rejected by design. Never weaken verification to make them pass. Use real sandbox payments to exercise callbacks. Before enabling live checkout, verify in sandbox: one-off checkout, a monthly subscription through at least one installment, webhook delivery, actual fees, a partial and a full refund, cancellation from PayPal's side, and a reconciliation pass after a simulated outage.
